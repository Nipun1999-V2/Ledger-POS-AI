# Ledger POS — Online POS System with Raw Material Inventory & AI with AWS

A full-stack point-of-sale system for a business that sells finished
products **and** raw materials, built with:

- **Backend:** Java 21, Spring Boot 3, Spring Security (JWT), Spring Data JPA, Flyway, PostgreSQL
- **Frontend:** Angular 18 (standalone components, no NgModules), Angular's own signals for auth state
- **AI features:** statistical demand forecasting + auto-generated analyst reports + real-time stock monitoring (details below)

```
pos-system/
├── backend/     Spring Boot API (Maven project)
└── frontend/    Angular 18 SPA
```

---

## 1. Feature list

### Core POS
- Barcode/search-free POS terminal: tap-to-add cart, quantity +/-, discounts, tax rate, multiple payment methods (cash, card, mobile wallet, bank transfer)
- Sells **finished products** and **raw materials sold directly** (e.g. fabric by the metre, flour by the kg) from the same screen
- Auto-generated invoice numbers, itemised receipts, sales history with date-range filtering and per-invoice detail view

### Inventory & raw materials
- Separate catalogs for **Products** and **Raw Materials**, each with SKU, category, cost/selling price, unit of measure, current stock, minimum stock level, reorder quantity
- **Recipes / Bill of Materials (BOM):** a product can be marked "made from raw materials" and linked to a list of raw materials + quantities consumed per unit. Selling one unit of the product automatically deducts the right amount of every ingredient from raw material stock — this is what lets a bakery/workshop/manufacturer sell finished goods while still tracking raw material consumption accurately.
- Every stock change (sale, restock, manual adjustment, recipe consumption) is written to an immutable **stock ledger** (`stock_movements`), so you always have a full audit trail of what happened to any item's stock and when.
- Manual restock and stock-adjustment actions from the UI

### Suppliers & categories
- Supplier directory (contact info) linked to raw materials
- Categories for products and raw materials, used for filtering/reporting

### Users & roles
- JWT-based login; roles: `ADMIN`, `MANAGER`, `CASHIER`
- Admins manage users; user list/creation endpoints are role-protected

### AI feature #1 — Next month's best sellers & reorder targets
`GET /api/ai/forecast` and `/api/ai/forecast/top-sellers`

For every item, the system:
1. Pulls the last N months (default 6) of actual units sold per month
2. Fits a linear regression (least-squares trend line) over that history, blended with a recency-weighted average so one unusual month can't dominate
3. Projects next month's expected demand, classifies the trend as `RISING` / `STABLE` / `FALLING`, and reports a confidence level based on how much history exists
4. Compares the forecast + a small safety buffer against current stock to suggest **how much to reorder now**

This answers exactly what you asked for: *"what will be our best-selling item next month, how much is our target, how much do we currently have."* It's implemented as a transparent statistical model (the same family of technique — trend-based demand forecasting — that most "AI-powered" inventory tools use under the hood) rather than a black-box model, so it's fast, explainable, and needs no external AI service or training data pipeline to work.

### AI feature #2 — Auto-generated analyst reports (daily/weekly/monthly)
`GET /api/ai/reports/today`, `/this-week`, `/this-month`, `/custom?start=...&end=...`

Each report includes: total revenue, order count, items sold, average order value, % change vs the previous equivalent period, top 5 and bottom 5 selling items, and a **plain-English narrative summary**.

- If you set an `ANTHROPIC_API_KEY` environment variable, the narrative is generated by calling Claude with the computed statistics, so you get a genuinely written analyst-style summary.
- Without a key, a rule-based narrative is generated locally from the same numbers (e.g. *"Over this week, the business made $X in revenue across N orders, up 12% vs the previous period. Product Y was the best seller..."*). The report always works — the LLM is an enhancement, not a dependency.

### AI feature #3 — Stock monitoring & low-stock alerts
- Every sale, restock, and adjustment immediately checks the item's new stock level against its configured minimum and opens a `StockAlert` if it's crossed
- A scheduled sweep (`app.stock.alert-check-cron`, default every 15 minutes) re-checks **all** products and raw materials, so nothing is missed even if data changed outside the normal flows
- `GET /api/stock-alerts` lists everything currently below its minimum; alerts auto-resolve when a restock brings stock back above the threshold, or can be resolved manually
- The Dashboard and Reports screens surface open alerts prominently, and the "reorder" figure from the AI forecast tells you not just *that* something is low but *how much* to bring in

## 2. Running it locally

### Prerequisites
- JDK 21
- Maven 3.9+
- Node.js 20+ and npm
- PostgreSQL 14+

### Backend
```bash
cd backend

# create the database
createdb pos_system
# or: psql -c "CREATE DATABASE pos_system;"

# edit src/main/resources/application.yml if your DB user/password differ
# from pos_user / pos_password, or override with env vars, e.g.:
export SPRING_DATASOURCE_USERNAME=postgres
export SPRING_DATASOURCE_PASSWORD=yourpassword

# optional — enables LLM-written analyst narratives instead of the
# built-in rule-based ones:
export ANTHROPIC_API_KEY=sk-ant-...

mvn spring-boot:run
```
The API starts on `http://localhost:8080`. Flyway runs the schema migrations
and seed data automatically on first start, including a default login:

```
username: admin
password: Admin@123
```
**Change this password immediately after first login in a real deployment**,
and replace `app.jwt.secret` in `application.yml` with a long random value
before going anywhere near production.

### Optional: load sample data
A full sample catalog (products, raw materials, suppliers, recipes) and
~5 months of randomized sales history are available separately so the
Dashboard, AI forecast, and AI reports have real data to show instead of
empty states. See the sample-data scripts provided earlier in this
conversation — run them with `psql -d pos_system -f <script>.sql` after
the backend has started at least once.

### Frontend
```bash
cd frontend
npm install
npm start          # ng serve, http://localhost:4200
```
`src/environments/environment.ts` points the frontend at
`http://localhost:8080/api` — update it if your backend runs elsewhere.

### Production build
```bash
cd frontend && npm run build          # outputs dist/pos-frontend
cd backend && mvn clean package       # outputs target/pos-backend.jar
```
Serve the built Angular files from any static host / reverse proxy (nginx,
etc.) configured to forward `/api/**` to the Spring Boot service, or drop the
built frontend into `backend/src/main/resources/static` and serve everything
from the single Spring Boot jar.

## 3. Data model at a glance

- `raw_materials` — things you buy in; can optionally be sold directly (`sellable_directly`)
- `products` — things you sell; can optionally have a `has_recipe` BOM against `product_recipe_items` → `raw_materials`
- `sales` / `sale_items` — one row per transaction, one row per line item (snapshotting name/price at time of sale)
- `stock_movements` — append-only ledger of every stock change, for any item, of any kind
- `stock_alerts` — open/resolved low-stock flags
- `categories`, `suppliers`, `users` — supporting reference data

## 4. Extending it further
- Swap `ForecastService`'s regression for a proper ML model (e.g. Prophet/ARIMA via a Python microservice) without touching any controller — it all flows through `ForecastItemResponse`
- Add barcode scanner input to the POS screen (it's just another way to call `addToCart`)
- Add receipt printing (browser print of the invoice modal, or a thermal printer ESC/POS integration)
- Multi-branch/location support by adding a `location_id` to stock and sales tables

## 5. Troubleshooting

**`401 Unauthorized` on login, even with the right password**
The password hash shipped in `V2__seed_data.sql` for the default `admin`
user needs to actually correspond to `Admin@123`. If you generated your
own seed data by hand, verify the BCrypt hash with the same library
Spring Security will check it with (e.g. Python's `bcrypt.checkpw`)
before trusting it — a hash that merely *looks* right will fail silently
with a generic "Invalid username or password" error. If you're stuck,
add a new Flyway migration (e.g. `V4__...sql`) with a fresh
`UPDATE users SET password = '<verified-hash>' WHERE username = 'admin';`
rather than editing an already-applied migration file, which will break
Flyway's checksum validation.

**Login works, but every other screen shows no data / "No X yet" placeholders**
This is almost always the browser blocking the request, not the backend
failing — curl/Postman bypass the browser's CORS enforcement entirely,
so a request that "works in Postman" can still be silently blocked in
the Angular app. Check:
1. Browser DevTools → **Console** for a red CORS error (not just the Network tab — a blocked request can still show up there with a misleading status).
2. `app.cors.allowed-origins` in `application.yml` matches your frontend's origin **exactly** (protocol + host + port, no trailing slash).
3. Every authenticated request carries a custom `Authorization` header, which triggers a browser **preflight `OPTIONS` request**. Make sure `SecurityConfig` explicitly permits it:
   ```java
   .authorizeHttpRequests(auth -> auth
       .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()
       .requestMatchers("/api/auth/**").permitAll()
       .anyRequest().authenticated()
   )
   ```
   Without that line, the preflight can get rejected before your actual `GET`/`POST` ever runs, depending on filter ordering — the symptom is identical to a silently-blocked request.

**Network tab shows the correct JSON response, but the table on screen stays empty**
At that point the HTTP layer is confirmed fine and it's a frontend
rendering/binding issue, not a backend one — check the browser Console
(not Network tab) for a runtime error such as an `NgFor` "not iterable"
error, do a hard refresh to rule out a stale cached JS bundle, and
confirm which exact placeholder is showing (an explicit "no data yet"
empty-state message means the component's local array is genuinely
empty — i.e. the `.subscribe()` callback never ran or ran with an
error — versus a table with the right headers but blank rows, which
points at a template binding bug instead).
